# S14 — Bulk edit & batch export — acceptance criteria

Conventions: a **batch** is an ordered list of image files (items) that share ONE style: the current document's `Project` (backdrop, border, shadow, canvas size, export options, and any fields later slices add). The batch holds file references, not decoded pixels; an item is decoded at full size only when it is shown in the main canvas or exported. Supported files are those of S1 (PNG, JPEG, HEIC, TIFF, WebP). The batch holds at most 500 items. Thumbnails in the **preview strip** have a long edge of 200 px and are rendered by `Renderer.render` from a downsampled proxy (long edge ≤ 256 px). Export file names use the S4 template (`{TEMPLATE}_{SCALE}_sunshot_{DATE}`) plus `{INDEX}` (1-based list position, zero-padded to the digit count of the batch size) and `{NAME}` (source file name without extension).

## S14-AC1 — Import many images from the open panel
Given the File ▸ Import Multiple… open panel (multiple selection, files and folders allowed)
When the user picks `a.png`, `b.jpg` and a folder
Then the batch contains a, b, then the folder's images, in that order
And the first new item is selected and shown in the main canvas
Test level: unit

## S14-AC2 — Dropping several files starts a batch; one file keeps the single-image flow
Given the editor window
When two or more supported image files are dropped on the canvas
Then they are added to the batch (no "Only one image" notice) and the drop is accepted
And when exactly one image file is dropped, it is opened as a single image exactly as in S1 (no batch)
And a drop containing no supported image and no folder is refused
Test level: unit

## S14-AC3 — Dropping a folder adds its images
Given a folder with `shot 10.png`, `shot 2.png`, `notes.txt`, `.hidden.png` and a subfolder
When the folder is dropped or chosen
Then `shot 2.png` and `shot 10.png` are added in Finder name order (numeric-aware)
And hidden files and subfolders are ignored (not recursive) and `notes.txt` is skipped
And a notice says "Skipped 1 file that isn't a supported image"
Test level: unit

## S14-AC4 — Duplicates and the 500-item limit
Given a batch that already contains `a.png`
When `a.png` (same path) is added again, or more files than the limit allows
Then duplicates are ignored, items beyond 500 are not added
And a notice reports how many were not added
Test level: unit

## S14-AC5 — One shared style for every item
Given a batch of three items and the current style
When the user changes any style control (e.g. corner radius or backdrop)
Then the change applies to all items (it is a change to the one `Project`), the strip thumbnails re-render with it
And it is one ordinary undo step, exactly as in single-image editing
Test level: unit

## S14-AC6 — Strip thumbnails use the same renderer
Given an item of 1600×1000 px and the current style
When its strip thumbnail is rendered
Then it is `Renderer.render` of the style with the downsampled proxy laid out at the item's true size (same canvas aspect as the full export, within 1 px), long edge 200 px
And no second drawing path exists for thumbnails
Test level: unit

## S14-AC7 — Lazy, downsampled decoding with bounded memory
Given a batch of large images
When thumbnails are created
Then each is decoded through ImageIO's downsampling straight from the file to a proxy whose long edge is ≤ 256 px (EXIF orientation applied, true oriented size read from the header)
And no full-size decode happens until an item is shown or exported
Test level: unit

## S14-AC8 — Unreadable items are flagged, not fatal
Given a batch containing a corrupt, truncated or missing file
When thumbnails are created or the item is selected
Then that item shows an error state with the reason ("The file is damaged or isn't an image.") and the other items are unaffected
And no alert interrupts the user
Test level: unit

## S14-AC9 — Selecting an item shows it in the main canvas
Given a batch of three items
When the user selects the second item (click, or ← / → in the strip)
Then the main canvas shows that image at full resolution with the shared style
And selecting creates no undo entry; undo/redo after switching items change only the style, never which image is shown
Test level: unit

## S14-AC10 — Remove items
Given a batch [a, b, c] with b selected
When b is removed
Then the batch is [a, c] and c is selected and shown; removing the last remaining item closes the batch and empties the canvas
And Close Batch empties the batch and keeps the image currently on the canvas
Test level: unit

## S14-AC11 — Reorder items
Given a batch [a, b, c]
When c is moved to the front (drag in the strip, or Move Left)
Then the batch is [c, a, b], and this order is the export order and the `{INDEX}` order
And moving the first item left or the last item right does nothing
Test level: unit

## S14-AC12 — Export all to a folder with the S4 options
Given a batch of three items, export options JPEG at 2× and a chosen folder
When Export All runs
Then one file per item is written to the folder in the item's own export size and the chosen format
And each file is byte-identical to exporting that image alone with the same style (`EditorSession.exportImageData`)
Test level: integration

## S14-AC13 — File names never clash
Given the template `{TEMPLATE}_{SCALE}_sunshot_{DATE}` and a batch of 12 items
When the names are generated
Then they are `screenshot_2x_sunshot_<date>_01.png` … `_12.png` (one date for the whole run, index padded to two digits)
And a template that already contains `{INDEX}` is used as written; `{NAME}` is the source file name
And when a file with the same name already exists in the folder (or two items would get the same name), `-2`, `-3`, … is added before the extension; existing files are never overwritten
Test level: unit

## S14-AC14 — Progress
Given an export of 10 items
When it runs
Then progress is reported before each item (current file name) and after each item, `completed` rises by one per item to 10 and the fraction ends at 1.0
And the export runs off the main thread (the UI stays responsive)
Test level: unit

## S14-AC15 — Cancel
Given an export of 10 items in progress
When the user presses Cancel after the third item
Then no further items are processed, the files already written stay, no partial file is left behind
And the summary reads "Cancelled — exported 3 of 10"
Test level: unit

## S14-AC16 — Per-item errors don't stop the batch
Given a batch of five items where the third file is corrupt and the fourth no longer exists
When Export All runs
Then the other three are exported, and the summary reads "Exported 3 of 5 — 2 failed" with each failed file's name and reason
And an item whose output would be too large is reported the same way
Test level: unit

## S14-AC17 — One item at a time
Given a batch export
When it runs
Then items are decoded, rendered, encoded and written strictly one after another (at most one full-size image decoded at any time)
And exporting 40 images of 3000×2000 px at 2× keeps memory bounded: the process footprint is flat over the last 20 items (≤ 64 MB more than after the first 20) and grows by at most 1.5 GB in all (perf stage)
Test level: unit

## S14-AC18 — Menus, strip and summary in the app
Given the running app
When the user chooses File ▸ Import Multiple… (⇧⌘O), picks images, then File ▸ Export All… (⌥⇧⌘E)
Then the preview strip appears under the editor with the thumbnails, count and Export All button; the progress bar and Cancel replace it while exporting; the summary offers Show in Finder
And Export All is disabled with no batch or while an export runs
Test level: app-smoke

## S14-AC19 — Accessibility of the strip
Given the preview strip
When used with VoiceOver and the keyboard
Then each thumbnail reads "Image 2 of 12, shot.png, selected" (or ", can't open" for a failed one), ← / → move the selection, ⌫ removes the selected item, and the context menu offers Move Left, Move Right and Remove from Batch
Test level: manual

## Open questions
- Zip output (the reference describes "zip or folder"): decided folder only — macOS users can compress a folder in Finder, and a zip writer would mean a new dependency or a hand-rolled format.
- Per-item style overrides: decided no — every item shares the one style, as the slice paragraph says.
- Parallel export: decided sequential (one item at a time) for bounded memory; a 2-way pipeline can come later if exports are too slow.
- Recursive folder import: decided no (top level only) so a dropped home folder can't pull in thousands of files.
